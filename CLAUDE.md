# ArchMind EA Platform — Frontend (ea-platform-ui)

React/TypeScript SPA for the ArchMind Enterprise Architecture platform. Deployed to Cloud Run by `.github/workflows/deploy.yml` on every push to `master` (tests → build → image to Artifact Registry → image-only deploy that keeps the service's existing sizing/access), default branch `master`. Sibling backend repo: `meganta/ea-platform` (branch `main`) — see that repo's `CLAUDE.md` for backend architecture, module status, and the shared working-style/policy notes (communication style, non-negotiable rules, standing policies) that apply equally here and aren't repeated in full below.

## Standing policy (agreed mid-session, applies to every new page/feature)

Every new page or feature includes, as standard: **unit tests, a help tip (or tips) explaining the feature in plain language, responsive design, and AR/EN support.** Not an afterthought bolted on later — part of building the thing.

## Architecture conventions

- **No shared `useApi()` hook.** Each page defines its own local `useApi()` closure. **Always wrap its returned object in `useMemo(() => ({...}), [deps])`** — an unmemoized return value causes a new object every render, which cascades into any `useCallback`/`useEffect` depending on it re-firing on every render (a real, previously-shipped bug: unwanted full re-fetches on every keystroke). Dependency array is `[]` if the closure only reads `localStorage`; it must include `token` if the closure reads a token from `useAuth()` directly.
- **Routing:** `react-router-dom` v7. Its package `exports` field is ESM-only and **not resolvable by Create React App's built-in Jest config** — when writing a test that needs `useNavigate`/`useSearchParams`/`Link`, mock the whole module: `jest.mock('react-router-dom', () => ({...}), { virtual: true })`. Don't try to render inside a real `<MemoryRouter>` in tests.
- **Labels need `htmlFor`/`id`, always.** The `form-group`/`form-label`/`form-input` pattern used throughout does not auto-associate a label with its input — this has been found and fixed as a real accessibility gap on 4+ pages already (LoginPage, RegisterPage, RepositoryPage's AssetModal, others). Add the pair explicitly on every new form field.
- **CSS: never mix the `border` shorthand with a specific side property (`borderBottom`, etc.) in the same style object.** `border: 'none'` resets all four sides; combined with a separate `borderBottom` on the same object, React's style diffing across renders can unpredictably clobber the intended side (found and fixed platform-wide, 9 pages, mostly tab-strip active-indicators). Use `borderTop/borderLeft/borderRight: 'none'` explicitly instead of the shorthand when you also need a specific `borderBottom`.
- **Responsive:** app shell (mobile sidebar), the `stat-grid-3/4/5/6` utility classes (`src/styles.css`) for any row of equal-width cards, table `overflowX: 'auto'` wrappers, and 3 side-panel patterns are already handled platform-wide. Follow those existing patterns for new UI rather than inventing new ones — inline styles can't respond to media queries, so anything that needs to reflow at a breakpoint belongs in a CSS class, not inline.
- **i18n:** `src/contexts/LangContext.tsx`'s `TRANSLATIONS` dict + `useLang()`'s `t()`/`isAR` + `dir={isAR ? 'rtl' : 'ltr'}` on the page root is the established pattern (see `StrategyPage.tsx`'s core workflow for a complete example). Given the government-platform accuracy stakes, prioritize correctness of the Arabic text itself over speed — don't guess at translations for domain terminology.
- **Persistent storage in artifacts** (if ever building a standalone artifact rather than a page in this app): no `localStorage`/`sessionStorage` — use the `window.storage` key-value API instead. Not applicable to this app's own pages, which do use `localStorage` directly for the auth token.

## Testing conventions

- `CI=true npx react-scripts test --watchAll=false` to run the suite (no separate Jest config needed — CRA's built-in one is used as-is).
- Mock `useLang`/`useAuth`/`useBranding` directly via `jest.mock()` on the context module rather than wrapping in real providers.
- `mockFetch` route-matching helper pattern: sort route patterns by string length descending (most-specific-first) before matching via `.includes()` — but watch the edge case where one route is a URL *prefix* and another is a *suffix* of the same longer URL (neither contains the other, so length-sorting alone doesn't disambiguate); use the full unambiguous path in that case.
- Watch for **duplicate button/text** between a page's tab strip and its own Dashboard "Quick Actions" shortcuts, or between a sidebar list item and its own auto-selected detail panel — disambiguate with `getAllByText(...)[0]` or a `waitFor` + length check rather than a bare `getByText` that will throw on multiple matches.
- **Always await the detail view actually rendering** after clicking into a list item before interacting with its tabs — `open()`-style handlers are async, and a subsequent click can race ahead of the fetch. "Fetch was called" is not sufficient; wait for real rendered content (e.g. a tab-strip element unique to the loaded detail view).
- Check whether text is gated by `t()` (renders as the raw key string under a test mock returning `(key) => key`) vs hardcoded literal English before writing an assertion against it.
- Wrap manually-dispatched DOM events (e.g. simulating an `<img onError>`) in `act(...)`.
- Click actual checkbox/radio `<input>` elements directly in tests rather than their wrapping `<label>` text — label-wrapped-input clicks don't always reliably propagate in jsdom.
- Mock `window.HTMLElement.prototype.scrollIntoView` globally if the page under test auto-scrolls anything (jsdom doesn't implement it).

## Current state (condensed, not a changelog)

- **19 pages**, all with unit test coverage (214 tests total) — though several pages' coverage is intentionally partial: `GovernancePage` (only the list view, not the 5-step wizard or 7-tab report view), `SettingsPage` (2 of 11 sub-tabs: Users, Governance Settings), `CopilotPage` (no live chat-send/SSE-streaming or voice-recording tests — those need `ReadableStream`/`MediaRecorder`/`getUserMedia` mocking not yet built).
- **Responsive UI:** foundational work done (app shell, stat grids, tables, 3 side panels); a full per-page sweep of remaining internal layouts has not been done.
- **AR/EN translation:** `StrategyPage`'s core workflow is translated. `EaViewsPage` is partly translated: everything added by the EA Views redesign (question, facts, states/evolution, toolbar, landscape, library open/search, matrix and canvas controls; `eaviews.*` keys) is AR/EN, while older parts (builder, authoring panels, comparison details) are still English. 7 other pages (`ConnectorHubPage`, `EaPlanningPage`, `MetaModelPage`, `AccessGovernancePage`, `CopilotPage`, `GlossaryPage`, `SharedViewPage`) have zero Arabic support — hardcoded English only.
- **EA Views viewer (`EaViewsPage` + `pages/eaviews/`):** driven by the backend `/dataset` response: the viewpoint `contract` (question, allowed visualizations), `presentation` (the visualization strip and empty-state meaning), and `insights` (facts tiles; selecting one narrows the view). States come from `/states` (Current/Transition/Target per programme; compare only within a line, "What changes" from `/evolution`). One AI entry, Ask ArchMind (grounded `/ai/explain` with the state on screen; "Continue in Copilot" prefills `/copilot?ask=`). Library Open goes straight to a private workspace view (`/open-viewpoint`, "Keep in My Views"); Customize keeps the builder. Use design-system tokens (`var(--accent)` etc.), not new hard-coded colours.
- **Public portal brand system** (landing + `/login`, `/register`, `/invite`, `/shared`): centralized in `src/brand/` (tokens, `.am-*` primitives, `BrandLogo`, `BrandPattern`, one outline icon set — see `src/brand/README.md`). Build new public UI on those tokens, never hard-coded colours. Logo system (horizontal/stacked/symbol × color/reverse/white/dark), favicons, PWA/app icons and social images are generated from `scripts/brand/` (vector masters in `public/brand/`) — regenerate there, never hand-edit or redraw. The authenticated app shell keeps its own `styles.css` theme.
- **Tenant settings:** every tenant-wide setting is read/written through the backend's Tenant Settings API (`/config/*`). Settings > Organization loads and saves profile, platform language (tenant locale) and framework/domains in scope in one call (`GET/PUT /config/organization`); don't write org settings to `/setup/profile` or `/ea-repository/framework-config` (read-only views).
- **ADM diagrams:** ADM shows no AI-drawn diagrams. `components/AdmOutputViews.tsx` shows the EA Views linked to each output (from `/adm-intelligence/outputs/:id/view-pictures`) with an Open in EA Views link; old outputs' diagram code blocks are hidden by `lib/diagramBlocks.ts`.
- **Copilot study cards:** when the Chief Architect prepares, refreshes or shows an Innovation study, `components/CopilotStudyCard.tsx` follows its generation (polls the study, section progress) and then offers the study's own Word/PowerPoint exports in the reader's language and an "Open in Innovation" link (`/innovation?study=<id>`, handled by InnovationPage). The Studies tab filters by author (`?author=USER|COPILOT|ALL`, default platform users) and badges Copilot-prepared studies. Study status/recommendation labels live in `components/studyLabels.ts`.
- **Copilot view attachments:** when Copilot renders an EA View for an answer, `components/CopilotViewAttachments.tsx` shows it under the message with PNG / PowerPoint downloads (`components/copilotViewExport.ts`, built from the attached SVG + rows only, never a re-query).
- **Copilot decks:** when Copilot presents an answer as a deck (`deck_prepare`), `components/CopilotDeckCard.tsx` shows its title, slide count, slide titles and notes, and downloads the PowerPoint from `/copilot/conversations/:id/decks/:deckId` (rendered by the backend in the tenant's branding; the card needs the open conversation's id). Strings `copilot.deck.*` (AR/EN).
- **Innovation (`InnovationPage`):** Radar, Favorites, Watchlist, Ideas, Studies, Profile tabs. A study can opt in to an EA Impact Analysis (create-form checkbox or the study's own toggle; run/re-run on its own): `StudyEaImpact` shows headline counts, each impacted domain with its objects, the other domains in one line each, and per domain the AI-chosen EA View picture (`StudyImpactViewFigure`, an `<img>` of the server-rendered SVG - never inline markup). The section editor never sends picture data back. Ideas tab (`pages/innovation/`: `IdeaAssessmentView`, `IdeaMatrix`, `ideaLabels`): pipeline stats, filters (priority, AI recommendation, sort, search, mine), list or Value / Ease matrix view, endorsements, problem-first create/edit form; the detail shows the full assessment (recommendation, weighted scorecard with reviewer adjustments, SWOT, benefits/KPIs, risk register, effort, strategy goals, affected EA objects, similar items, limitations), follows a running assessment, has a discussion, and "Start a detailed study" opens the study form linked to the idea. Study downloads go through `lib/studyExport.ts` (`fetchStudyExport`), which keeps asking while the API answers 202 PREPARING for a large study.
- **Strategy Intelligence (`StrategyRefreshPage` + `components/StrategyImpactRegister.tsx`):** the overview leads with the backend's impact register (`refresh.impact`): synthesis headline/overview/key messages, totals, and a domain heat map; a domain opens the Architecture Impact tab's register (filters by domain/level/type/named-in-documents; each object shows the strategy statements behind it, which open the evidence drawer), the domain's EA View picture (`<img>` of the server SVG) and the names the documents use that the Repository does not model. Refreshes analysed before the register say so and offer "Re-run analysis" (`POST /rerun`, a new refresh over the same documents). Source documents are streamed (`/documents/:sourceId/content` as a blob), never signed URLs. Overview: "What the documents say" (facts by kind -> Strategy Map) vs "What ArchMind concludes" (conclusions by kind -> the tab that acts on them), and a collapsed "Limits of this analysis" worded from the backend's coded `limits` (`components/StrategyRefreshSections.tsx`). Strategy Map = statements by kind (structure first, then assessment content), each with "Drives N impacted objects" -> the register filtered to that statement. What Changed explains when there is no approved baseline. Conclusions everywhere use `components/StrategyFindingCard.tsx` (recommended action, priority, Affects = named records, Based on = statements, what publishing would do). Execution & Outcomes = plans / ADM cycles / outcomes sections; Review & Publish = step header (Review -> Activate -> Publish), groups by kind with "Approve all pending" (one reason, each decision recorded). Strings: `strategy.refresh.impact.*`, `.fact_type/.fact_group.*`, `.limits.*`, `.map.*`, `.card.*`, `.execution.*`, `.review.*`, `.steps.*` (AR/EN).
- **Strategic alignment & KPI measurement** (Strategy page home: Strategy refreshes / Strategic alignment / KPI measurement; `components/StrategicAlignmentPanel.tsx`, `components/KpiMeasurementPanel.tsx`, client `lib/strategy-alignment.ts`, strings `strategy.align.*`, `strategy.kpi.*`, `strategy.type.*`, `strategy.home.*`): the alignment shows where each level came from (provisional drafts, Repository fallbacks), carried-over decisions, the matrix (the workbook's 11 columns), links to confirm/reject/add (only allowed level pairs), gaps, and strategic KPI results / roadmap progress, with Excel export. KPI measurement: units owning KPIs (EA department first), reported flag, frequency, target, due-period measures with status, monthly measures, period reports + Excel. Each measure has a comment and evidence (web links, files - `components/KpiEvidenceDialog.tsx`, the 📎 button next to the measure; files download through the API, never a storage URL); the report table shows the period's comments/evidence and those of the months it covers. A refresh's strategy type is set on create and on the refresh title bar.
- **Repository object page (`RepositoryPage` + `pages/repository/`):** clicking an object (or ✏) opens it as a full page in place of the list (`?asset=<id>[&mode=edit]`, browser Back returns; `?assetId=` deep links still work). `AssetProfileScreen` loads `/ea-repository/assets/:id/profile`: Overview (facts, completeness, relationship summary, findings, roadmap, synced source), Attributes (`AssetAttributesView`: Meta Model groups, empty ones "not recorded", other recorded data), Relationships (`AssetRelationshipsView`: every allowed relationship per direction with its links, which open that object; other links), Attachments. Edit (`AssetEditor`, `AttributeField` - one typed input per attribute type, also used by the create modal) edits core fields, every attribute (PUT sends the full metadata, keeping keys the Meta Model does not define) and every relationship slot (candidate picker of the right type, add/remove, relationship attributes, single-valued slots replace), reporting any link change that failed; values and links the Meta Model does not define can be changed/removed there too. Every attribute and relationship carries an origin tag (`OriginTag`: Meta Model - tooltip names the Meta Model version and definition code - / Not in Meta Model / Core field) in view and edit. The list and object page use the Innovation look (`rp-*` / `ap-*` classes in `AssetProfile.css`: header band, tab strip on navy-light, cards, stat tiles - the list's status tiles filter by status). Strings `repository.profile.*`, `repository.list.*` (AR/EN).
- **User invitations (`UsersPage`):** after inviting, the modal says whether the email was sent (backend `emailDelivery`) and always shows the link with Copy; Pending Invitations copies the token link from `GET /users/invitations/:id/link` (never built from the invitation id) and offers Resend (renews the link). Tenant web addresses live in one place, `lib/tenantHosts.ts` (hostname -> tenant; used by sign-in, invite links shown/copied, and `InviteAcceptPage`, which after creating the account sends the person to their tenant's address to sign in - a session on another address would not carry over); the backend has no stored tenant address yet, so emailed links still use the shared URL. Strings `users.invite_*`, `users.resend*` (AR/EN).
